# ADR-0001: Hand-Written Recursive Descent Parser

- **Status**: Accepted
- **Date**: 2026-03-20
- **Deciders**: Project maintainers

## Context

COBOL compiler の Parser 実装方式を選定する必要がある。
主な候補は以下の2つ:

1. **手書き再帰下降パーサー** — コードで直接パーサーロジックを記述する
2. **パーサージェネレータ** — ANTLR, lalrpop, pest 等のツールで文法定義から自動生成する

## Decision

**手書き再帰下降パーサーを採用する。**

## Rationale

### 1. COBOL 文法の文脈依存性

COBOL の文法は文脈依存性が極めて高い。

- 同一キーワードが文脈により識別子としても使われる（例: `MOVE` がデータ名になるケース）
- `COMPUTE` 文の `=` と条件式の `=` の区別など、先読みだけでは解決しにくい曖昧性が多数存在する
- これらは LL / LALR の文法クラスに素直に収まらず、パーサージェネレータでは大量のセマンティックアクションやハックが必要になる

### 2. エラー回復の柔軟性

本プロジェクトでは `DiagnosticReporter` にエラーを蓄積して解析を継続する方式を採用している。

- 手書きパーサーでは「同期ポイントの配置」「特定トークンまでのスキップ」など、文脈に応じた細かいエラー回復制御が可能
- パーサージェネレータの自動エラー回復は汎用的であり、COBOL 特有の回復戦略を組み込みにくい

### 3. COBOL 固有のレキシカル問題

- **Fixed format**: カラム 1-6 シーケンス番号、カラム 7 インジケータ、カラム 8-72 コンテンツ領域
- **PICTURE 句**: `PIC 9(3)V99` のような特殊構文は通常のトークン化ルールが適用できない
- これらは `SourceReader` とレキサーの連携で処理しており、手書きであることでパーサーとの統合が自然に行える

### 4. プロダクションコンパイラの実績

主要なプロダクションコンパイラ（GCC, Clang, rustc, Go, TypeScript）はいずれも手書きパーサーを採用している。GnuCOBOL は yacc/bison を使用しているが、文法ファイルが巨大で保守性に課題があることが知られている。

## Alternatives Considered

### パーサージェネレータ（ANTLR, lalrpop, pest 等）

**Pros:**

- 文法定義がフォーマルで、曖昧性の検出が可能
- プロトタイピング段階では素早く動作するパーサーを得られる
- 文法がきれいな言語（JSON, SQL サブセット等）には非常に有効

**Cons:**

- COBOL の文脈依存的な文法を表現するために、文法定義が複雑化・ハック的になる
- エラー回復の制御が限定的
- PICTURE 句など特殊構文の処理に別途ハンドリングが必要
- 生成コードのデバッグが困難
- ツールへの依存が増える（ビルドプロセスの複雑化）

## Consequences

**Positive:**

- COBOL の複雑な文脈依存文法に対して柔軟に対応可能
- エラー回復戦略をきめ細かく制御できる
- レキサー・パーサー間の連携が自然で、PICTURE 句等の特殊処理を統合しやすい
- 外部ツールへの依存がなく、ビルドプロセスがシンプル
- パフォーマンスの直接制御が可能

**Negative:**

- パーサーのコード量が多くなる（文法定義に比べて）
- 文法変更時の修正が手動になる（自動再生成はできない）
- 文法のフォーマルな曖昧性検出ができない
